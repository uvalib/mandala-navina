# Deferred Notes

Items noted during spike work or development that need to be addressed in downstream
implementation. Each file is one logical issue.

## Tracking: GitHub Issues (decided 2026-10-08)

Deferrals are **internal developer project tracking**, not user-facing work, so they are
tracked as **GitHub Issues** in this repo (Jira stays for user-facing work; this supersedes the
earlier "each note maps 1:1 to a Jira ticket" intent). A practical second reason: not everyone on the team has developer Jira access (Than does not), while everyone already works in this repo. The note and the issue split the job:

- **The note** (this directory) holds the *why* — context, findings, options. It is reviewed in
  PRs and is what session startup reads. Never edit history away; add a dated section.
- **The issue** holds *status* — owner, blocked/not, discussion, linked PRs.

Rules:

1. **Any deferral can be promoted to an issue at any time, with or without an owner.** An
   unassigned issue is a normal state: it means *free for any of us to pick up* or *needs a group
   decision* (the first line says which), and session start/close list unassigned issues so they
   get seen. Use `./scripts/promote-deferral.sh <note> [--assignee LOGIN] [--decision]`; it opens
   the issue (labelled `deferred`, body is a link and status only), and writes `**Issue:** #N`
   into the note's header. A note with an owner or a start trigger should be promoted. A note
   with neither can stay doc-only (`**Issue:** none`); doc-only notes are reviewed periodically
   and promoted when someone wants to track them.
2. Close the issue when the work ships or the deferral is dropped, and add a dated *Resolved*
   section to the note.
3. **This repo is public, and so are its issues.** Titles and bodies follow the same rule as
   notes: say that a problem exists and who to ask, never what it is. Anything tracked in the
   private docs repos (see [non-public-documentation](../non-public-documentation.md)) gets no
   public issue, or a stub that names no detail.
4. If a deferral turns into something users will notice, move the tracking to Jira.

`session-start-check.sh` lists open `deferred` issues; `session-close-check.sh` warns about
notes missing an `**Issue:**` header. Existing notes get the header as they are next touched —
there is no bulk backfill.

## Naming convention

`CATEGORY-or-topic-short-description.md` (the file name is free-form; the `Category` header is what classifies the note)

Examples: `kmaps-widget-ux.md`, `migration-tibetan-unicode.md`, `api-url-strategy.md`

## File header

```
# Title
**Category:** one to three values from the vocabulary below, comma-separated
**Raised during:** Spike N / Phase N
**Issue:** #N (GitHub Issue, label `deferred`) — or `none`
**Priority:** High / Medium / Low
**Owner:** name(s), `unassigned`, `group`, or `n/a (resolved)`
```

### Category vocabulary

The first value is the note's primary category (it decides which section of "Open items"
below the note appears in); list up to two more if the note genuinely spans them. The
vocabulary is fixed but extensible: to add a category, add a line here and a section below,
rather than writing free-text tags.

| Category | Covers |
|---|---|
| `migration-av` | AV (Audio-Video) site migration: field fidelity, Kaltura, transcripts |
| `migration-images` | Images site migration: fields, IIIF, paragraphs |
| `migration-texts` | Texts site migration (footnotes, book structure) |
| `migration-sources` | Sources site migration (none yet — site not migrated) |
| `migration-general` | Cross-site migration: orphans, legacy-nid convention, OG/Group content model, user migration, URL mapping |
| `access-control` | Group permissions, visibility enforcement, `content_editor` / contributor tiers |
| `auth` | SAML, OAuth2, SimpleSAMLphp, NetBadge |
| `solr-search` | kmassets, kmterms, transcripts, solr-proxy, search quality |
| `infrastructure-deploy` | Terraform, CodePipeline, Ansible, RDS, Redis, reindeer_x, s3-sync |
| `security` | Vulnerabilities and exposures specifically, not just infrastructure |
| `miscellaneous` | Anything that fits none of the above |

### Owner rules

- State ownership only when the note says it unambiguously (an existing `Owner:` line or a clear
  "ASSIGNED to X"). Up to 2–3 names, comma-separated (`Yuji, Dave`).
- Being present for, or raising, a discussion is **not** ownership.
- `group` means the group has to address it together in session (see
  [Awaiting a team decision](#awaiting-a-team-decision)).
- A resolved, done, fixed, superseded or closed note is `n/a (resolved)`, even if someone is
  credited with building the fix. It moves to "Resolved notes" below.
- Otherwise `unassigned` — free for anyone to pick up (see Tracking, above).
