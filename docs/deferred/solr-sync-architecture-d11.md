# Solr Sync Architecture for D11
**Area:** solr / kmassets / kmterms
**Raised during:** Session 2026-06-12 (kmterms/kmassets architecture investigation)
**Jira:** (add when available)
**Priority:** High

## Background

The D7 Mandala platform maintains two Solr indices:

- **`kmterms`** — The KMaps ontology: subjects, places, and terms. Owned and written by the external KMaps Rails applications (Andres Montano / Casa Tibet Guatemala). Drupal only reads from this index.
- **`kmassets`** — All asset descriptions across the Mandala platform. Contains two distinct populations.

### Two populations in kmassets

**Population 1 — KMaps-derived assets** (`asset_type`: `subjects`, `places`, `terms`):
One kmasset entry per kmterm. These are generated 1:1 from kmterms and kept in sync by the `kmaps-solr-sync` service (Node.js, runs as the `reindeer_x` Docker container). They make KMaps taxonomy terms themselves discoverable as assets in search.

**Population 2 — Drupal content assets** (`asset_type`: `audio-video`, `images`, `texts`, `visuals`, `sources`, `collections`):
One kmasset entry per Drupal node. These are generated by the `shanti_kmaps_fields` module on node save.

### Full D7 sync pipeline

**Content assets (Drupal → kmassets):**
1. Node saved in Drupal → `shanti_kmaps_fields` writes JSON doc to `private://solrdocs/`
2. `clsync` (watching that directory inside the Aegir/hostmaster container) detects the file
3. `synchandler` (Perl) uploads the JSON file to S3 (`mandala-ingest-{env}-inbound/kmassets-inbound/`) via `rclone`
4. S3 notification → SQS → ECS pipeline (transform → Solr update)

The `synch` (shell) and `synchandler` (Perl) scripts live in the `reindeer_x` container and are now committed at `kmaps-solr-sync/docker/reindeer_x/files/usr/local/bin/`.

**KMaps-derived assets (kmterms → kmassets):**
1. UDP packet triggers `kmaps-solr-sync` (Node.js, `reindeer_x` container)
2. Service reads changed kmterms entries from the kmterms Solr index (query window configurable, defaults to `!schema_version_i:40`)
3. Transforms kmterms documents into kmasset documents
4. Writes directly to kmassets Solr index

The `kmaps-solr-sync` source is now in the monorepo at `kmaps-solr-sync/`.

## Problems for D11

### 1. Content asset sync (Drupal → kmassets)

The D7 mechanism relies on:
- `shanti_kmaps_fields` writing JSON to `private://solrdocs/` (method 1 in the D7 module)
- `clsync` watching that directory inside the Aegir container
- `synchandler` uploading to S3

In D11, Aegir is gone. The equivalent pipeline needs to be designed:
- Does the D11 `shanti_kmaps_fields` module write JSON to a watched path, or POST directly to the ECS ingest S3 bucket?
- What replaces `clsync` + `synchandler`? Options: direct S3 upload from Drupal, a sidecar container, or a Drupal queue worker that posts to SQS.

### 2. KMaps-derived asset sync (kmterms → kmassets)

The `kmaps-solr-sync` service needs to be modernized:
- The UDP trigger mechanism is fragile and undocumented operationally
- No cron or automatic re-sync — requires a manual UDP packet
- Code notes from 2021 flag it as "not production ready"
- Needs proper triggering (cron, HTTP endpoint, or event-driven from KMaps Rails apps)
- Needs to be integrated into the AWS ECS deployment alongside the other ingest tasks

### 3. Operational ownership

The `kmaps-solr-sync` service was previously in the `shanti-uva` GitHub org and effectively outside the UVA Library deployment pipeline. It is now in `mandala-navina` but its deployment is still on the legacy dev server (`mandala-drupal-dev-0`). It needs to be:
- Brought into the Terraform/ECS infrastructure
- Given proper environment config (not baked-in credentials)
- Given a reliable trigger mechanism

## Recommended next steps

1. **Spike:** Prove what D11 `shanti_kmaps_fields` should use for Solr indexing — direct ECS/S3 POST, or Search API Solr with a custom backend.
2. **Design:** Define the D11 equivalent of the `synch`/`synchandler` pipeline for content assets.
3. **Modernize `kmaps-solr-sync`:** Add HTTP/cron trigger, make config fully env-var driven, integrate into ECS.
4. **Clarify kmterms ownership:** Confirm with Andres/Than whether KMaps Rails apps will push to the ECS ingest S3 buckets directly, or whether `kmaps-solr-sync` remains the bridge.
