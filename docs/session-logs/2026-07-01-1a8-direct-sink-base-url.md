## User — 2026-07-01 14:57

I just wonder, since we are creating a new uid-space, is there an advantage to using a new id-format that distinguishes old and new?

---

## Claude — 2026-07-01 14:58

There's a real advantage, and it actually simplifies the consumer analysis problem.

**The case for a new format:**

If you're doing a full reindex at cutover anyway, every consumer that stores uids is already broken — there's no free pass. Given that, a distinguishable format gives you something valuable during the transition: you can query the staging index and see exactly which entries are D7-era vs. D11 at a glance. Cleanup becomes `DELETE uid:images-d11-*` rather than trying to reason about nid ranges. And consumers that haven't been updated yet are immediately identifiable — their stored `images-{old-nid}` references simply won't resolve.

**The most principled option: UUID-based**

Drupal nodes already have a `uuid` field — stable, globally unique, no collision risk across asset types. `images-{uuid}` (e.g. `images-a1b2c3d4-e5f6-7890-...`) would work identically for migrated and new-native D11 content, and eliminates the nid concern permanently. The downside is it changes the character of the uid significantly — longer, not human-readable in the way `images-1028396` is.

**A simpler option: generation marker**

`images-d11-{nid}` — same structure, explicitly versioned. Easy to pattern-match, self-documenting, and nid is still readable. Less elegant than UUID but low-friction to implement.

**The tradeoff to name clearly:**

A new format means the consumer analysis we just scoped becomes *mandatory before cutover* rather than just advisory. Right now with same-format uids, a consumer that happens to get the same nid by coincidence might accidentally work. With a new format, there's no accidental compatibility — every consumer must be updated deliberately.

My lean is UUID — it solves the identity problem permanently for all future asset types too, not just Images. But it's a bigger statement. What's your instinct?

## Claude — 2026-07-01 15:59

Yes, and it's worth thinking carefully about what "out of sync" means before building it. Three distinct failure modes:

1. **Missing** — node exists in Drupal (published) but has no doc in Solr. The most common failure: hook fired, Solr write failed silently.

2. **Orphaned** — doc exists in Solr but the Drupal node was deleted and the delete hook failed. Less common but causes ghost results.

3. **Stale** — doc exists in both but the Solr `node_changed` timestamp is behind the Drupal node's `changed` value. Means an update was lost.

**Feasibility:** All three are detectable because we store `node_changed` in the Solr doc and the uid encodes the nid. The approach:
- Missing: page through Drupal nids in batches, bulk-query Solr (`uid:(images-11-1 OR images-11-2 OR ...)`), report gaps
- Orphaned: cursor-page through Solr `uid:images-11-*`, verify each nid exists in Drupal
- Stale: same as missing pass but also fetch `node_changed` from Solr and compare to the node's `changed` field

**My recommendation:** build it in two passes. A `kmassets:audit` command that runs all three checks and reports counts/discrepancies, with a `--fix` flag that reindexes/deletes the affected docs. The stale check is the most expensive (requires fetching timestamps from both sides) — I'd include it but make it opt-in with `--check-stale`.

```bash
ddev drush kmassets:audit                # report missing + orphaned
ddev drush kmassets:audit --check-stale  # also report stale docs
ddev drush kmassets:audit --fix          # report + repair
```

     class KmassetDirectSink {
       public function __construct(
         protected readonly ClientInterface $httpClient,
         protected readonly KmassetDocBuilder $docBuilder,
         protected readonly ConfigFactoryInterface $configFactory,
         protected readonly LoggerChannelFactoryInterface $loggerFactory,
       ) {}

       public function indexNode(NodeInterface $node): ?string { // returns uid or null

         if ($doc === NULL) return NULL;
         $this->solrPost([$doc]);
         $this->loggerFactory->get('mandala_kmassets_sync')
           ->info('Indexed @uid to kmassets master.', ['@uid' => $doc['uid']]);
         return $doc['uid'];
       }

       public function deleteNode(NodeInterface $node): bool {
         $uid = $this->uidFor($node);
         if ($uid === NULL) return FALSE;
         $this->deleteByQuery("uid:$uid");
         return TRUE;
       }

       public function deleteByQuery(string $query): void {
         $this->solrPost(['delete' => ['query' => $query]]);
       }

       public function uidFor(NodeInterface $node): ?string {
         $bundles = $this->configFactory->get('mandala_kmassets_sync.settings')->get('bundles') ?? [];
         $config = $bundles[$node->bundle()] ?? NULL;
         if ($config === NULL) return NULL;
         return $config['service'] . '-11-' . $node->id();
       }

       public function configuredBundles(): array {
         return array_keys(
           $this->configFactory->get('mandala_kmassets_sync.settings')->get('bundles') ?? []
         );
       }

       protected function solrPost(array $payload): void {
         $url = $this->masterUpdateUrl();
         $response = $this->httpClient->post($url, ['json' => $payload]);
         $body = json_decode((string) $response->getBody(), TRUE) ?? [];
         if (($body['responseHeader']['status'] ?? -1) !== 0) {
           throw new \RuntimeException('Solr update failed: ' . json_encode($body['error'] ?? $body));
         }
       }

       protected function masterUpdateUrl(): string {
         $url = $this->configFactory->get('mandala_kmassets_sync.settings')->get('solr_master_url');
         if (!$url) throw new \RuntimeException('solr_master_url is not configured.');
         return rtrim($url, '/') . '/update?commit=true';
       }
     }
