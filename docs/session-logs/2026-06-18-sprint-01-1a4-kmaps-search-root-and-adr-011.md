The decision gating on Spike 3 is **Q1 in today's brief: which inheritance approach do we use for Group collections → subcollections?**

Spike 3 proved the *structural* half (Group `collection`/`subcollection` types, one-level nesting via a `parent_collection` entity-ref, basic access control) but explicitly **did not** resolve the **inheritance model**:

1. **Visibility inheritance** — private parent ⇒ subcollections private by default (overridable to public).
2. **Membership inheritance** — subcollection inherits all parent members (additive locally).

Both must match D7 `og_subgroups` behavior. The brief's table:

| Option | Membership | Visibility | D11 status | Verdict |
|---|---|---|---|---|
| A — entity-ref only | ✗ | ✗ | proven | insufficient |
| B — `ggroup` | ✓ | ✗ (custom) | **not D11-ready** | blocked |
| C — `subgroup` | ✓ | ✗ (custom) | unconfirmed | risky |
| **D — entity-ref + custom hooks** | ✓ | ✓ | no dep risk | **recommended (~2–3 d)** |
| E — ggroup/subgroup + custom visibility hook | ✓ | ✓ | dep-blocked | revisit later |

Key fact driving the recommendation: **no Group contrib option provides visibility inheritance out of the box** — visibility always needs custom logic, which weakens the case for taking on `ggroup`/`subgroup` as a dependency.

Why it gates everything else: the Images model (just built) chose Paragraphs for access inheritance, but paragraph access only holds if the *parent image's* access is correct — and that comes from Group collection visibility. So the 1a.7 image migration's access story depends on resolving this. That's why it's first on the agenda before any more collections work happens.

## Q2 unpacked — what "structural Group types now" actually means

The question is whether to extend the CMI baseline we just committed with a few more config files **before** we know how inheritance will be implemented, or to leave the entire Group/collections layer empty until Step 1b.

### What "model structural Group types" includes (and doesn't)

If we go now, the additions to `drupal/config/sync` would be roughly:

| Config | What it does | Risk |
|---|---|---|
| `group.type.collection` | Group bundle for top-level collections | None — bundle definition |
| `group.type.subcollection` | Group bundle for child collections | None |
| `field.field.group.collection.parent_collection` (or only on `subcollection`) | Entity-reference field pointing a subcollection at its parent | None — pure field config |
| `group_content_type.group_content_type.collection-group_node-shanti_image` | Plugin enabling `shanti_image` nodes to be members of `collection` groups (and same for `subcollection`) | None — relation declaration |
| Group permissions / role configs per type | Member/anonymous/outsider role permission grids | Low — declarative |

What it **excludes** (deliberately):
- Custom hooks for visibility inheritance (the Option D logic)
- Custom membership-sync code
- The `visibility_overridden` flag mechanism
- Any migration code from D7 `og_collection_ref` → Group membership

So "structural" = the **schema** (group bundles, fields, relations, permissions). "Inheritance" = the **behavior** (hooks + custom logic). Q2 is asking whether to land the schema now and the behavior later.

### Case for (a) "model now"

- **It's the same kind of low-risk CMI work we just finished** — declarative bundle/field/plugin config, no contrib dependencies, no custom code. Nothing in this list pre-commits us to anything Option D doesn't already need.
- **Closes a real gap in the Images baseline.** Right now `shanti_image` has no group-relation config, so even a manual test of "put an image in a collection" isn't possible against the committed baseline. The skeleton lets the team start exercising the model.
- **Surface for 1a.7 migration planning.** The image migration script needs target Group bundles to map D7 `field_og_collection_ref` against. Having the bundles in config makes 1a.7 design concrete instead of hypothetical.
- **Reversible.** It's CMI config — if the inheritance design forces a structural change later, we edit the config and re-export. The cost of "wrong now" is small.

### Case for (b) "hold for 1b"

- **ADR 009 deliberately decoupled** Step 1a (public win) from Step 1b (auth/groups). The whole point was to ship Images-as-a-readable-thing without entangling auth complexity. Adding Group config to 1a partially blurs that line — even if the *behavior* stays out, the *config* is now Group-aware.
- **Permissions matrices are easy to get wrong.** Group's per-bundle permission grids are detailed, and getting them right depends on the inheritance approach (Option D's hooks need certain hooks/permissions to exist). Landing them now means a permissions revision when 1b actually implements inheritance.
- **The 1a.7 migration argument cuts both ways.** Images can be migrated in 1a *without* group membership and have it backfilled in 1b — that's exactly the OG→Group sequencing 1b.2 already implies.

### Hidden third option worth naming

**(c) Half-step: bundles + relation, no permissions yet.** Land `collection` / `subcollection` group types and the `group_node:shanti_image` relation plugin, but defer the permission-grid config to 1b.2 when inheritance behavior lands. This keeps the *schema* visible (helps 1a.7 migration design and team familiarity) without committing to a permission model that Option D's hooks may need to revise.

### What I'd point at

The strongest argument either way: **how soon will the 1a.7 migration script be written?** If 1a.7 is near-term (this sprint), having the Group bundles in config now makes the migration target real instead of a placeholder — argues for (a) or (c). If 1a.7 will wait for 1b anyway, the case for landing config now weakens — argues for (b).

What's your read on the 1a.7 timeline? That probably decides it.

## What `private://solrdocs/` actually represents

It's the **D7 Drupal module's write output**, before the rest of the pipeline runs:

```
shanti_kmaps_fields (Drupal) → private://solrdocs/*.json
                                ↓
                         clsync → synchandler → S3 → SQS → ECS → Solr
```

Comparing those JSON files tells you whether D11's **field-extraction and Drupal-side write logic** matches D7's. That's a useful test, but it stops well before the doc is actually in Solr.

## What it doesn't catch

- **Post-JSON pipeline behavior** — `clsync`/`synchandler`/the ECS step may transform, validate, or reject docs in ways tied to assumptions about the JSON shape. A D11 write that *looks* identical at the JSON layer could behave differently downstream.
- **Solr ingestion itself** — schema validation, analyzer chain, type coercion, NFC/NFD normalization. The "indexed" doc isn't the same as the "written" doc; Solr transforms on the way in.
- **Query-time behavior** — two docs with different shapes can satisfy the same query, and two docs with identical shapes can return different results if any of the analysis chain shifted.
- **D11 may not produce `private://solrdocs/` at all.** That's a D7 implementation detail. If 1a.8 / reindeer_x writes directly to Solr (or via SQS in a different format, or via Lambda), there's no JSON intermediary to compare. The format is an artifact of the pipeline being replaced.

## What the contract actually is

The **only** layer D7 and D11 are obliged to produce identically is the Solr index — that's the surface ADR 004 declared the source of truth. Everything before that is implementation detail and is allowed to differ. So the verification has to ultimately land at the Solr layer.

## "Shadow index" can mean several things

I conflated them in my previous answer. The real options:

| Form | Cost | What it verifies |
|---|---|---|
| **Long-running parallel prod index** (e.g., `kmassets_d11_shadow` writing alongside prod) | High (infra, ops) | Full real-traffic divergence over time |
| **Short-lived staging index** that D11 writes into during test cycles | Low/medium | Per-batch verification against fixtures |
| **Ephemeral CI Solr** spun up per test run, fed a fixture set | Low | Schema + ingestion contract; no live drift detection |
| **Offline JSON comparison only** (what I implied) | Trivial | Drupal write logic — but blind to ingestion + queries |

The last one alone isn't enough. The middle two — staging or CI Solr — are usually sufficient and don't require a production-parallel shadow. So the *cheap* answer is: a staging Solr core that D11 writes into during verification runs, fed the same source content. That's a more limited "shadow" than what I implied at first, but it's still genuinely indexing the docs, which JSON comparison can't substitute for.

## The practical recommendation, corrected

A two-layer verification, both needed:

1. **JSON-layer diff** (if D11 retains a serialized intermediary): cheap regression check on Drupal-side write logic. Fast feedback for 1a.8 development.
2. **Solr-layer fixture verification** in a staging/CI Solr: capture prod docs for ~50 representative nodes as the golden reference; D11 writes its output to a staging core; per-doc field diff + query-result parity against the captured fixtures.

A long-running production-parallel shadow is an optional third layer (catches real-traffic drift) but not the minimum bar. The Dave Goldstein conversation is mostly about whether (1) the prod Solr can host an extra core for staging verification cheaply and (2) the deployed pipeline pattern, not about needing a permanent shadow.
